# Spot the Bot

A live, team-based human-vs-AI detection game for leadership sessions and events.

## How it works

Each table grabs one device and picks a team name. Every team works through a shuffled bank of text samples — for each one the group decides: was this written by a **human** or generated by an **AI**? The host starts a shared **10-minute countdown** for the whole room. When time runs out, the team with the most correct answers wins. Ties are broken by total answer time (faster wins).

The host is a facilitator, not a contestant. The host device shows a live standings board and controls (Start / End / Reset) — it never appears on the leaderboard.

## Architecture

- **Frontend**: Next.js App Router, deployed to Vercel.
- **State store**: Firebase Realtime Database (RTDB). All teams subscribe to the live tree via the Firebase JS SDK; the client is read-only.
- **Server-authoritative API routes**: Next.js route handlers use the Firebase Admin SDK to write scores and game state. Clients can never write to RTDB directly — the database rules deny all client writes (see `database.rules.json`).
- **Anti-cheat question split**: `lib/questions.server.ts` holds the full question bank including answers, reveal text, and sources. It is guarded by `import "server-only"` — the build fails if it is ever imported into client code. `lib/questions.public.ts` holds prompts only (no answers) and is safe for the browser.
- **Key encoding**: RTDB paths cannot contain `:`, so `game:state` and `team:<id>` keys are encoded as `game__state` / `team__<id>` on the wire and decoded on read.
- **Session identity**: `localStorage` keys `stb_role` and `stb_team` persist a device's role and team ID across page reloads so a dropped phone rejoins the same team instead of spawning a duplicate.

## Local development

```bash
cp .env.example .env.local
# Fill in all values in .env.local (see table below)
npm install
npm run dev
```

Open `http://localhost:3000`.

## Environment variables

| Variable                            | Visibility           | Description                                                                                     |
| ----------------------------------- | -------------------- | ----------------------------------------------------------------------------------------------- |
| `NEXT_PUBLIC_FIREBASE_API_KEY`      | Public (browser)     | Firebase web API key                                                                            |
| `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN`  | Public (browser)     | Firebase auth domain                                                                            |
| `NEXT_PUBLIC_FIREBASE_DATABASE_URL` | Public (browser)     | RTDB URL (also used by Admin SDK)                                                               |
| `NEXT_PUBLIC_FIREBASE_PROJECT_ID`   | Public (browser)     | Firebase project ID                                                                             |
| `NEXT_PUBLIC_FIREBASE_APP_ID`       | Public (browser)     | Firebase web app ID                                                                             |
| `FIREBASE_SERVICE_ACCOUNT`          | Secret (server only) | Full service account JSON, single-line or base64-encoded. Used by Admin SDK to write to RTDB.   |
| `HOST_TOKEN`                        | Secret (server only) | Passphrase for host controls (Start / End / Reset). Checked server-side on every host API call. |

`NEXT_PUBLIC_*` variables are safe to expose to the browser — they are Firebase's public client identifiers by design. The real security boundary is the RTDB rules, not key secrecy.

## Firebase setup

1. Create a Firebase project and enable Realtime Database.
2. Apply the RTDB rules from `database.rules.json` in the Firebase console under **Realtime Database → Rules**. These rules allow any client to read but deny all client writes — all writes go through the server-side Admin SDK. JSON does not support comments; this README is the place to document them.
3. Go to **Project settings → Service accounts → Generate new private key** to get the service account JSON. Paste the entire JSON as a single-line string (or base64-encode it) into `FIREBASE_SERVICE_ACCOUNT`.
4. Go to **Project settings → Your apps → Web app → SDK config** and copy the values for the `NEXT_PUBLIC_FIREBASE_*` variables.

## Deploy to Vercel

1. Set all environment variables in the Vercel project dashboard (Settings → Environment Variables). The `NEXT_PUBLIC_*` variables apply to all environments; `FIREBASE_SERVICE_ACCOUNT` and `HOST_TOKEN` are secrets — mark them accordingly.
2. Push any branch to get a **preview deployment**. Push to `main` to trigger a **production deployment**.
3. Run a **Reset game** (host control) before a live session to clear any practice scores.

Tests run with [Vitest](https://vitest.dev/). The pure game logic in `lib/game.ts` is covered by unit tests; API routes and the client hook are tested with mocked Firebase dependencies.
